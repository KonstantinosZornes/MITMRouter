# MITMRouter

[English documentation](README.en.md)

> **按身份选择稳定出口的超高性能本地流量路由器**
>
> 面向高并发 LLM/API 流量，识别请求中的 Marker 或订阅账号，为不同身份选择合适的上游出口。业务客户端无需修改 API 地址、SDK 或请求代码，只需要把网络出口指向本机。

MITMRouter 的 MITM 根证书（中间人证书）和私钥在**首次启动时自动生成**，并只保存在本地数据目录。所有运行数据和密钥材料——包括配置、凭据、账号映射、审计记录和 CA 材料——均保存在本地 SQLite `router.db`，不依赖云端数据库或额外数据服务。数据由部署者掌控，安全边界清晰；同时必须像保护密钥一样保护 `router.db`。

MITMRouter 解决的是一个很具体的问题：**同一个账号要长期从稳定的出口访问上游 API，不同账号又要能够独立路由，而且不能要求每个客户端都改一遍。**

```text
Marker / 订阅账号
        │
        ▼
稳定的路由身份
        │
        ▼
上游平台的 session / sid
        │
        ▼
尽可能稳定的出口 IP
```

- **超高性能路由链路**：面向高并发设计，HTTPS + TLS 解密 + HTTP/2 并发 64 时实测约 **833–921 IOPS**；
- **客户端接入不侵入业务**：不改 Base URL，不改 SDK，不改业务请求内容；
- **按账号保持粘滞**：同一个 Marker 或订阅账号持续使用同一条逻辑出口；
- **多出口统一编排**：适配 DataImpulse、Decodo、1024proxy、Resin 以及通用模板；
- **可运营、可审计**：内置 Web 管理台、访问审计、TTFB、更新记录和 Prometheus 指标；
- **本地优先、安全可控**：密钥和运行数据不依赖云端存储，由部署者自行管理；
- **部署简单**：SQLite 单文件存储，单二进制交付，不依赖额外数据库。

## 它解决什么问题

在 LLM/API 业务中，出口选择通常同时受到身份、稳定性和客户端改造的限制：

| 业务问题 | 直接结果 | MITMRouter 的处理方式 |
|---|---|---|
| 同一账号需要稳定出口 | 请求在不同出口之间漂移，容易触发风控或会话失效 | 将 Marker/账号映射为稳定的路由身份，再生成平台 session/sid |
| 不同账号需要隔离 | 所有请求共用一条出口，账号之间无法区分 | 为不同身份分别计算路由，并支持账号级出口绑定 |
| HTTPS 中的身份不可见 | 只看得到加密隧道，无法根据 API Key 做路由 | 在本地路由层按目标规则解密并识别 Marker |
| Token 会轮换 | Token 变化后被误认为新账号，出口随之变化 | 将订阅账号与短期 AT/RT 解耦，Token 轮换不必更换出口 |
| 出口平台格式不统一 | 每个平台都要单独写一套接入逻辑 | 统一管理平台模板和会话参数注入 |
| 缺少运行可见性 | 出口、状态码、延迟和失败原因难以排查 | 管理台集中管理，审计记录请求结果和 TTFB |

它的职责是**做路由决策和出口编排**：决定请求从哪条出口连接出去；目标站看到的业务 URL、请求头、请求体、响应头和响应体不会被项目主动改写。

## 核心能力

### 1. Marker 路由与账号级粘滞

- 默认识别 `Authorization: Bearer ...`、`x-api-key`、`api-key`、`x-goog-api-key` 等常见凭据；
- 支持按目标主机、路径片段和请求规则控制身份识别范围；
- 未命中订阅账号时，使用 Marker 计算稳定身份，兼容纯 Marker 路由；
- 命中账号映射后，按逻辑订阅账号路由，而不是按短期 Token 路由；
- 路由盐保存在本地数据中，进程重启不会让所有身份无故重新分配；
- 需要整体切换出口时，可以主动换盐，作为风险控制和故障逃生手段。

### 2. 客户端无需改业务配置

客户端不需要修改目标 API 的 Base URL、SDK 或请求代码。完成本机 CA 信任配置后，将系统或应用的网络出口指向 MITMRouter 的路由入口即可。

目标是否允许访问由目标 ACL 先行决定：

- 不允许的目标在本地返回 `403`，不会连接目标；
- 允许的 HTTPS 目标在本地完成 TLS 解密和路由决策；
- 路由层只使用识别结果选择出口，不主动修改放行请求的 URL、请求头、响应头或响应体。

### 3. 多平台出口统一接入

MITMRouter 把内部路由身份转换为不同出口平台所需的会话格式：

| 上游平台 | 会话格式 | 适用说明 |
|---|---|---|
| DataImpulse | `sessid.<account>` | 将路由身份写入 DataImpulse 会话参数 |
| Decodo | `session-<account>` | 使用平台的 session 参数保持会话 |
| 1024proxy | `sid-<account>` | 使用平台的 sid 参数保持会话 |
| Resin | `Platform.<account>` | 使用平台用户名格式承载路由身份 |
| Generic | 自定义模板 | 适配同类会话参数格式 |
| Plain | 不注入会话参数 | 普通出口模式，可按 sticky/random 绑定 |

上游连接支持 `http://`、`https://`、`socks5://` 和 `socks5h://`。平台会话本身有生命周期，MITMRouter 能保证的是稳定地使用同一个会话标识；会话在平台侧过期回收后，出口 IP 仍可能变化。

### 4. 账号与出口编排

账号管理支持从 CLIProxyAPI、Sub2API 等同步源拉取，也支持手动登记。账号命中后可以：

- 绑定多个普通出口；
- 为不同出口设置优先级；
- 在粘滞和随机策略之间选择；
- 让账号级绑定优先于默认路由；
- 在删除账号时级联清理绑定关系。

这样可以把“账号是谁”和“出口从哪里走”分开管理，适合 Token 轮换、出口池切换和多账号隔离。

### 5. 管理、审计和安全控制

- Vue3 内置管理台，中英双语；
- 上游出口新增、测试、启用、停用和默认出口切换；
- 测试上游的出口 IP 和地理位置；
- 按时间、关键词、账号指纹、上游和状态码查询访问审计；
- 记录总耗时和首字节时延（TTFB）；
- 可选 Prometheus `/metrics`；
- 目标 ACL、私网和云元数据地址保护；
- 入站认证、管理台 HTTPS 和敏感信息日志保护；
- 更新记录用于查看同步源和账号状态变化。

## 路由链路

```text
AI / API 客户端
        │ HTTP 请求或 HTTPS CONNECT
        ▼
本地路由入口 :55666
        │
        ├─ 目标是否被 ACL 放行？
        │    ├─ 否：本地 403，不连接目标
        │    └─ 是：继续本地 TLS 解密和身份识别
        │
        ├─ 提取 Marker 或订阅账号凭据
        ├─ 计算稳定路由身份 / 查询账号映射
        ├─ 命中账号绑定？选择绑定出口
        └─ 否则选择默认出口并注入平台会话参数
        │
        ▼
上游出口平台
        │ DataImpulse / Decodo / 1024proxy / Resin / Generic / Plain
        ▼
目标 API
```

### 为什么 HTTPS 路由需要本地解密

CONNECT 隧道建立后，目标请求位于 TLS 加密内容中。上游出口只能看到隧道连接，无法直接读取其中的 `Authorization` 或其他 Marker，因此无法仅靠上游平台完成按账号路由。

MITMRouter 在本地受控地终结 TLS，先识别身份并完成出口选择，然后建立到上游的连接。这个过程服务于路由决策，不改变目标站收到的业务 URL、业务请求头、请求体，也不改变目标站返回的响应头和响应体。

## 快速开始

### 1. 构建并启动

构建需要 Go ≥ 1.22 和 pnpm：

```bash
./scripts/build.sh
./bin/mitmrouter-linux-amd64 -data ./data
```

首次启动会随机生成管理员口令，并且只在启动日志中打印一次，请立即保存。

默认监听地址：

| 用途 | 地址 |
|---|---|
| 客户端路由入口 | `127.0.0.1:55666` |
| 管理台 | `127.0.0.1:55667` |

打开 `http://127.0.0.1:55667/ui`，使用首次启动时生成的口令登录。

### 2. 在管理台完成最小配置

按下面顺序操作即可跑通第一条请求：

1. **基础设置**：确认 Marker 提取规则和入站认证；
2. **下载 CA**：下载 `ca.pem`，安装到需要进行 HTTPS 身份识别的系统或客户端信任区；
3. **上游出口**：选择平台、填写 `base_url` 和凭据；
4. **测试出口**：确认连通性、出口 IP 和地理位置；
5. **设为默认**：将可用出口设为默认上游；
6. **接入客户端**：将客户端或系统网络出口指向 `http://127.0.0.1:55666`；
7. **确认结果**：请求完成后，在访问审计页查看账号指纹、上游、状态码和耗时。

如果路由入口启用了入站认证，使用带凭据的地址，例如：

```text
http://user:pass@127.0.0.1:55666
```

### 启动参数

README 只保留启动时必须知道的参数；运行期设置的完整填写说明见 [参数填写指南](PARAMETERS.md)。

| 参数 | 默认值 | 说明 |
|---|---|---|
| `-data` | `./data` | 数据目录，包含 `router.db`、CA 和运行期数据 |
| `-addr` | `127.0.0.1:55666` | 客户端路由入口监听地址 |
| `-admin-addr` | `127.0.0.1:55667` | 管理台监听地址 |
| `-trace-file` | 空（关闭） | 本地调试，将明文请求/响应流式写入文件；不脱敏，生产环境谨慎开启 |
| `-log-level` | `info` | `debug` / `info` / `warn` / `error`；普通日志不会记录 Marker 和 Token |

监听地址只由启动参数控制，修改后需要重启；其余运行期设置保存在 SQLite，并由管理台管理。

## 管理台能做什么

管理台不是单纯的参数页面，而是路由规则、出口和运行状态的统一入口。

| 页面 | 解决的问题 |
|---|---|
| 基础设置 | 配置 TLS、入站认证、Marker 提取、粘滞策略、TTL、ACL、私网保护、审计保留和 metrics |
| 上游出口 | 管理多家出口平台，查看凭据掩码、测试出口 IP、启停出口和设置默认路由 |
| 账号管理 | 同步或登记订阅账号，关联账号与出口，处理 Token 轮换和账号级路由 |
| 访问审计 | 按时间、关键词、账号指纹、上游和状态码筛选请求，查看总耗时和 TTFB |
| 更新记录 | 查看同步源拉取、账号映射和相关状态变化 |

### 目标 ACL：决定哪些目标允许访问

ACL 控制的是“哪些目标可以进入转发路径”。支持四种条目：

- 单个 IP：`1.2.3.4`；
- CIDR 网段：`10.0.0.0/8`；
- 精确域名：不包含子域；
- 通配符域名：`*.openai.com`，匹配任意层级子域但不匹配主域。

判定顺序：

```text
命中黑名单        → 本地 403，拒绝访问
白名单非空且未命中 → 本地 403，拒绝访问
其余目标          → 放行并进入身份解析和路由流程
```

ACL 拒绝发生在 DNS、身份解析和出站连接之前；放行请求保持原始业务语义，不改写 URL、请求头、响应头或响应体。另有默认开启的 `block_private_targets` 私网保护：即使 ACL 放行，访问本机、内网和云元数据地址仍会返回 `403`，并且会检查域名解析结果，避免通过 DNS 绕过。

## 性能表现

> **以下是 MITMRouter 自身路由链路的受控实测，不是公网出口、住宅网络或真实模型服务的性能承诺。**

在本机虚拟上游、每次上传和下载各 64 KiB 的场景下：

- HTTP 单请求平均完整时延约 **3.2–3.4 ms**，吞吐约 **290–310 IOPS**；
- HTTPS CONNECT + 本地 TLS 解密 + HTTP/2 单请求平均完整时延约 **4.5–5.5 ms**，吞吐约 **180–224 IOPS**；
- HTTPS 并发 64 时约 **833–921 IOPS**，平均完整时延约 **68–76 ms**，是吞吐和延迟较平衡的档位；
- HTTPS 并发 256 最高观测到 **1033 IOPS**，但平均完整时延超过 **230 ms**，最慢请求超过 **700 ms**；
- 所有样本均通过 URL、请求头、请求体、响应体 SHA-256 和 sticky ID 校验，**errors = 0**。

### 结果汇总

| 场景 | 并发 | IOPS | 平均 TTFB | 平均完整时延 |
|---|---:|---:|---:|---:|
| HTTP 裸连 | 1 | 289.9–309.8 | 2.37–2.55 ms | 3.22–3.45 ms |
| HTTP 裸连 | 8 | 579.4–637.2 | 9.32–10.37 ms | 12.50–13.76 ms |
| HTTP 裸连 | 64 | 447.5–912.7 | 60.96–123.6 ms | 67.59–139.4 ms |
| HTTP 裸连 | 256 | 563.3–805.9 | 236.1–369.1 ms | 292.4–405.7 ms |
| HTTPS + TLS 解密 + HTTP/2 | 1 | 181.8–223.6 | 3.17–3.95 ms | 4.47–5.50 ms |
| HTTPS + TLS 解密 + HTTP/2 | 8 | 528.1–617.8 | 8.71–10.29 ms | 12.91–15.04 ms |
| HTTPS + TLS 解密 + HTTP/2 | 64 | 833.2–920.9 | 43.19–49.53 ms | 68.15–76.01 ms |
| HTTPS + TLS 解密 + HTTP/2 | 256 | 994.8–1033 | 177.8–191.8 ms | 233.8–239.5 ms |

完整原始数据见 [性能实测报告](docs/009-performance-test-report.md)。

## 安全边界与已知限制

- **粘滞是尽力而为**：平台 session 到期或被回收后，同一账号可能获得新的出口 IP；
- **不处理 UDP/QUIC**：启用 HTTP/3 的客户端可能绕过本路由，可在系统层限制 UDP 443；
- **证书固定无法解密**：使用 certificate pinning 的客户端不适合进入本地身份解析范围；
- **保护好 `router.db`**：其中包含 CA 私钥、凭据材料、账号映射和审计数据，持有数据库的人可能解密经过本路由的 HTTPS 流量；
- **谨慎开启 `-trace-file`**：该模式写入明文请求和响应，不做脱敏，只适合受控调试；
- **公网部署必须加固**：管理台绑定非回环地址时应配置 HTTPS、限制来源并设置入站认证；
- **ACL 是目标访问控制**：黑名单命中或白名单未命中会本地返回 `403`；私网目标保护是独立的安全检查，ACL 放行也不能绕过它；
- **不承诺外部服务性能**：本 README 的 benchmark 不代表真实住宅出口、公网链路或模型服务容量。
