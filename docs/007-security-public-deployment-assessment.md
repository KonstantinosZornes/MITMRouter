> **这份文档说的是：如果 MITMRouter 放到公网，会有什么风险、哪些风险决定先不管、接下来准备改什么。**  
> **PD-02、PD-03、PD-06 已完成代码修改和后端测试；PD-01、PD-04、PD-05、PD-07 仍按已接受风险处理。**

## 已接受、这轮不改的风险

### PD-01：首次公网启动窗口

现有部署流程允许服务先绑定公网地址，再通过网页配置 TLS 和接入口密码。

这意味着在配置完成前：

- 别人可能把你的服务器当成免费的公网转发出口用；
- 管理台第一次登录可能走明文 HTTP；
- 网络链路上的人可能看到初始管理员口令或登录会话。

**决定：接受风险，本轮不改代码、不改启动流程。**

> 这只是记录“知道有这个风险且选择接受”，不是说它已经安全了。

### PD-04：数据目录权限

`data/router.db` 里有很敏感的数据，例如：MITM 根证书私钥、管理员会话密钥、上游出口凭据和同步源 API Key。

新建目录时程序会使用较严格的权限，但如果这个目录原来就存在且权限偏宽，程序不会主动把它改严。

**决定：接受风险，本轮不加权限修复。**

仍然建议运维侧做到：只有运行 MITMRouter 的账户能读取 `data/`；不要把 `router.db` 放到共享目录、公开备份或工单附件中。

## 接下来要改的两件事

### PD-02：HTTPS 管理台的登录 Cookie 要加保护

#### 现在的问题

登录后，浏览器会保存一个名为 `sticky_session` 的 Cookie。它相当于“已登录管理员的通行证”，有效期是 7 天。

现在这个 Cookie 有：

- `HttpOnly`：网页里的 JS 不能直接读它；
- `SameSite=Lax`：降低其他网站直接借用它发请求的风险；

但没有 `Secure`。这表示它可能被浏览器通过 HTTP 明文请求发出去。

如果管理台走公网 HTTP，网络路径上的人拿到这个 Cookie 后，不用知道管理员密码，也能冒充管理员进入后台。

#### 改完后应该怎样

| 访问管理台的方式 | Cookie 行为 | 是否能登录 |
|---|---|---|
| `https://你的域名:55667` | Cookie 加 `Secure`，只会随 HTTPS 发送 | 可以 |
| `http://127.0.0.1:55667` | Cookie 不加 `Secure`，保留本地 HTTP 用法 | 可以 |
| `http://公网地址:55667` | 仍然是明文登录，不安全 | 不应作为公网部署方式 |

#### 已完成的修改

1. 签发登录 Cookie 时，把当前请求传进去。
2. 如果这次请求本身是 HTTPS，就设置：

   ```go
   Secure: r.TLS != nil
   ```

3. 登录和“快到期后自动续期”两处，都使用同一套判断。
4. **不要直接写死 `Secure: true`**。项目默认的本地管理台是 `http://127.0.0.1:55667`；写死后，本地 HTTP 登录会在部分浏览器中失效。
5. 如果未来由 Nginx/Caddy 在前面做 HTTPS、MITMRouter 自己只收到 HTTP，需要单独设计“可信反向代理”配置；不能直接相信任何客户端传来的 `X-Forwarded-Proto`。

#### 这项改动不解决什么

它不会让公网 HTTP 管理台变安全。公网管理台仍然应该使用 HTTPS；更好的做法是只绑定 `127.0.0.1`，通过 SSH Tunnel 或 VPN 访问。

---

### PD-03：默认禁止经本服务访问内网地址

#### 现在的问题

现在的逻辑是：如果目标是内网地址，MITMRouter 不经住宅上游，而是让**服务器自己直接连接**。

原本是为了兼容内网使用，但如果接入口对公网开放，拿到接入凭据的人就可能借你的服务器访问它所在网络中的服务。

例如：

```text
http://127.0.0.1:2375/       # 服务器本机服务
http://10.0.0.5:9200/        # 内网服务
http://192.168.1.1/          # 内网网关
http://169.254.169.254/      # 云服务器元数据服务
```

#### 哪些地址算“内网地址”

默认要拦住：

- `localhost`、`127.0.0.1`、`::1`；
- `10.x.x.x`、`172.16.x.x` 到 `172.31.x.x`、`192.168.x.x`；
- IPv6 私网地址，例如 `fd00::/8`；
- 链路本地地址，例如 `169.254.x.x`、`fe80::/10`；
- CGNAT 地址 `100.64.0.0/10`；
- `0.0.0.0`、多播地址等不应由客户端访问的地址。

#### 改完后应该怎样

| 设置 | 客户端请求内网地址时的结果 |
|---|---|
| 默认：开启“禁止经本服务访问内网和本机地址” | 直接拒绝，不连接目标 |
| 管理员手动关闭该开关 | 允许 MITMRouter 服务器直接连接目标；接入用户也可能访问服务器本机和内网服务 |

#### 已完成的修改

1. 新增设置：`block_private_targets`。
   - 默认值：`true`；
   - 设置页名称：**禁止经本服务访问内网和本机地址**；
   - 说明：开启时禁止访问；关闭时允许 MITMRouter 服务器直连私网/回环目标；
   - 关闭开关时显示高风险警告：持有接入凭据的人可以通过 MITMRouter 访问服务器本机和内网服务。
2. **删除旧设置 `private_target_direct`**，不保留兼容开关。
   - 从 `settings.Snapshot`、默认设置、SQLite 初始化、设置读取/保存、管理 API DTO、前端类型、设置页和中英文文案中全部移除；
   - 程序启动时会删除旧数据库里的同名 SQLite 设置键；
   - 不从旧值迁移，因为旧值默认就是 `true`，会让升级后的实例继续意外放行内网。
3. `block_private_targets=true` 时：
   - 普通 HTTP 转发请求返回 `403`；
   - CONNECT 请求在建立隧道前返回 `403`；
   - HTTPS 解密后的请求也再次检查，防止绕过；
   - 错误内容统一为“已禁止访问内网或本机地址”，不泄露服务器的内网信息。
4. `block_private_targets=false` 时，恢复当前“私网/回环目标由 MITMRouter 服务器直接连接”的兼容行为。
5. 记录安全审计事件 `private_target_blocked`，方便在管理台知道有人尝试访问内网目标。
6. 不能只检查用户写出来的 IP。
   - 例如用户请求 `http://internal.example/`，它也可能在 **MITMRouter 所在机器**解析到 `10.0.0.5`；
   - 因此程序会在本机 DNS 解析和本机最终拨号时检查；本机解析到内网地址就拒绝，并用同一份解析结果拨号，避免 DNS 地址在中间被替换。
7. 经上游出口时，域名最终由上游出口所在网络解析。上游出口自己的内网访问控制由上游出口负责；本项目不尝试把本机解析的 IP 强塞给上游出口，也不把上游出口的内网当作 MITMRouter 的防护范围。
8. 这个限制只针对“访问目标”。管理员配置的上游出口地址可能本来就在内网，不应被误拦。

#### 必须验证的场景

- 默认状态下，请求 `localhost`、`127.0.0.1`、私网 IPv4/IPv6、链路本地和云元数据地址都被拒绝；
- 普通 HTTP、CONNECT、HTTPS 解密后请求都无法绕过；
- 目标服务没有收到请求；
- 域名在 MITMRouter 本机解析到私网地址时也被拒绝；
- 管理员关闭“禁止经本服务访问内网和本机地址”后，才允许私网直连；
- 普通公网 API、现有上游出口、ACL 和 MITM 功能不受影响。

## 以后再看、暂不处理的事项

### PD-05：同步源地址

管理员可以配置同步源地址，程序会带着同步源 API Key 去请求它。管理员账号一旦被盗，攻击者可能把地址改成自己的服务器，从而收到原来的 API Key。

**决定：接受风险。** 利用这个能力需要先拿到管理员会话；按当前决定，这属于“系统已经被攻破后才会发生的影响”，不作为单独的修复项处理。本轮不限制同步源地址，也不修改临时测试复用已保存 API Key 的行为。

> 接受该风险不表示 API Key 不重要，而是明确把防护重点放在管理员会话本身（PD-02）上：一旦后台会话失守，攻击者本来就已经拥有配置和读取后台资源的高权限。

### PD-06：登录失败记录占内存

#### 为什么要保留这项记录

登录失败记录不是审计日志，也不保存密码。它只是临时记住“某个来源 IP 最近输错了几次、要等多久才能再试”，用来减慢管理员密码的暴力猜测。

当前行为大致是：第一次输错允许重试；继续输错会逐渐延长等待时间；正确登录后清掉这条记录。这个防暴力破解能力应该保留。

#### 现在的问题

当前记录放在进程内存的一个按 IP 索引的 map 里，没有固定容量上限。攻击者若不断换不同 IP 发送错误密码，每个 IP 都可能留下一条记录，时间长了会占用越来越多内存。

#### 已完成的修改

目标是：**继续限制暴力破解，但不让失败记录无限吃内存。**

1. 把现在的普通 `map[string]*attempt` 换成有两个限制的缓存：
   - **最大条目数**：例如最多保存 10,000 个来源 IP；达到上限时，淘汰最久没有活动的记录；
   - **自动过期时间**：一个 IP 在最长退避时间（当前 15 分钟）后仍没有新失败，会在下次访问或定期清扫时删除。
2. 保持现有登录体验：
   - 第一次失败不锁；
   - 连续失败按指数增加等待时间，最大仍为 15 分钟；
   - 正确登录后立即清掉该 IP 的失败记录；
   - 同一个 IP 在缓存被淘汰或自然过期后，重新从第一次失败开始计算。
3. 缓存满时优先淘汰“已经不在等待期内”的旧记录；如果全是活跃记录，再淘汰最久未访问的一条。这样攻击者不能通过大量假 IP 让 map 无限长大。
4. 不记录密码、请求体或完整认证信息；只保存来源 IP、失败次数、最后失败时间和锁定截止时间。
5. 管理台部署在反向代理后时，来源 IP 的获取要单独处理：不能直接信任客户端可伪造的 `X-Forwarded-For`。只有明确配置可信反向代理后，才读取并使用它传来的真实客户端 IP。
6. 程序内缓存只能缓解单进程内存问题，不能替代网络层防护。公网部署仍建议在 Nginx/Caddy/防火墙/CDN 层给登录接口加连接数和请求频率限制。

#### 要验证什么

- 同一个 IP 连续输错时，等待时间仍会逐步增加；
- 正确登录后，该 IP 能立刻恢复正常；
- 过期记录会被自动删除；
- 同时构造超过最大条目数的不同 IP 后，缓存大小不会超过上限；
- 淘汰一个旧 IP 后，该 IP 再次输错会按首次失败处理；
- 没有把密码、Cookie 或请求内容写进缓存、日志或 API 返回值。

### PD-07：调试 trace 文件

使用 `-trace-file` 后，请求头、请求体、响应头、响应体都会写进文件，其中可能包括 API Key 和用户内容。

**决定：接受风险。** 这是管理员显式传入启动参数后才会开启的调试功能，默认关闭；按当前决定，不对它增加脱敏、权限校验或使用限制。

> 接受的前提是：启用者知道 trace 文件包含敏感内容，并自行负责文件位置、权限、清理、备份和日志采集范围。即使接受风险，也不应在生产环境无必要地开启它。

## 上线前最少确认什么

当前版本准备公网部署时，至少要确认：

- 公网 HTTP 管理台仍然不安全；HTTPS 管理台应使用正确证书；
- 接入端口需要强密码认证；
- 默认会禁止接入用户访问服务器本机、内网和云元数据地址；如果管理员关闭这个开关，就重新承担 PD-03 的风险；
- PD-01、PD-04、PD-05、PD-07 是已明确接受、但没有修复的风险；
- `-trace-file` 是已接受的调试风险；启用者自行负责敏感文件的保存和清理。
