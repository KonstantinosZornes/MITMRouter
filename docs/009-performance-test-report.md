# MITMRouter 最新性能实测

- **测试日期**：2026-08-27
- **测试对象**：MITMRouter 当前工作区 + 根目录独立 `benchmark`
- **测试内容**：HTTP 裸连、HTTPS CONNECT + MITM + HTTP/2
- **请求模型**：每次请求上传 64 KiB，下载 64 KiB；每条都校验 URL、headers、请求体、完整响应体 SHA-256 和粘滞 ID
- **重复次数**：每个场景、每档并发连续测约 1 秒，共 2 轮

## 先说结果

这次测的是“MITMRouter 自己这段链路”有多快，不访问公网，也不连真实住宅出口或模型服务。

- HTTP 单请求大约 **290–310 IOPS**，完整请求平均约 **3.2–3.4 ms**；
- HTTPS 单请求大约 **180–224 IOPS**，完整请求平均约 **4.5–5.5 ms**；
- 并发 8 时，HTTP 和 HTTPS 都能达到约 **528–637 IOPS**；
- 并发 64 时，HTTPS 约 **833–921 IOPS**，HTTP 在本机上波动较大，约 **448–913 IOPS**；
- 这轮最高观测值是 HTTPS、并发 256 的 **1033 IOPS**；
- 所有写入本报告的数据均为 **0 errors**，每条请求都通过完整性校验；
- 并发 256 时已经明显排队：平均完整时延约 **234–406 ms**，最慢一次约 **0.7–1.0 秒**。这不是适合追求低延迟的档位。

一句话：这台机器在这个“本地虚拟上游 + 64 KiB 双向数据”的受控场景下，HTTPS 在 **64 并发附近**是比较平衡的档位；继续堆到 256 能提高 IOPS，但时延会显著上升。

## 1. 这次到底测了什么

链路如下：

```text
测试客户端
  │ HTTP 裸请求，或 HTTPS CONNECT
  ▼
MITMRouter
  ▼
benchmark（本机独立进程）
  ├─ 解析 MITMRouter 真正发来的粘滞会话 URL
  ├─ 返回解析出的 sticky ID
  ├─ 返回固定 64 KiB 响应
  └─ 不连接任何目标地址、不访问公网
```

`benchmark` 不是直接在代码里 mock 一个返回值。它是真实监听 TCP 端口的独立进程：

- HTTP 场景收到绝对式转发请求；
- HTTPS 场景收到 `CONNECT benchmark.test:443`，然后在隧道中完成 TLS 和 HTTP/2；
- 它从实际收到的 `Proxy-Authorization` 重建粘滞会话 URL，并按 DataImpulse 格式取出 `sessid`；
- 客户端会校验返回的 sticky ID 是否等于 MITMRouter 根据 Marker 推导出的 ID。

所以本报告能说明 HTTP/HTTPS 两条转发链路、MITM、上游 CONNECT、粘滞凭据注入和 64 KiB 数据转发是否工作正常；**不能**说明真实住宅出口、真实公网或真实模型服务的性能。

## 2. 指标怎么理解

| 指标 | 人话解释 |
|---|---|
| 平均首字节（TTFB） | 客户端开始请求后，多久拿到响应头；越小表示整条转发链路越早开始回数据 |
| 平均完整时延 | 请求发出到完整读完并校验 64 KiB 响应体的平均时间 |
| 最大完整时延 | 这一组里最慢的一次完整请求时间；用来看偶发卡顿 |
| IOPS | 每秒完成且完整校验通过的请求数。这里是“64 KiB 写入 + 64 KiB 读取”的完整操作，不是磁盘 I/O |
| errors | 网络、协议、粘滞 URL、body hash 或内容校验失败的次数；任何非 0 都不能当作有效性能结果 |

每档会先预热连接，然后用固定 worker 数发请求。并发档位为：

```text
1 → 8 → 64 → 256
```

**怎么看 HTTP：**

- 单请求约 3 ms；
- 并发 8 时 IOPS 翻倍，但平均完整时延升到约 12–14 ms；
- 并发 64、256 的波动已经比较大，说明这台测试机开始受到调度、连接和 CPU 竞争影响；
- HTTP 并发 64 的两轮差异很大，因此不能只拿其中 912.7 IOPS 当稳定容量，要以更多轮次的中位数判断。

**怎么看 HTTPS：**

- 与 HTTP 相比，单请求多了 CONNECT、两段 TLS 和 MITM 的成本，所以单请求平均约多 1–2 ms；
- 并发 8 的 IOPS 已与 HTTP 接近，说明连接预热后 TLS/MITM 没有造成数量级性能损失；
- 并发 64 的结果相对稳定，约 833–921 IOPS，平均完整时延约 68–76 ms；
- 并发 256 的 IOPS 接近或超过 1000，但平均首字节已约 180–192 ms，最慢完整请求超过 700 ms；如果业务看重响应开始时间，不应以这个档位作为常用配置。

## 4. 数据完整性结论

这次写入表格的请求全部满足：

- 请求 URL、path、query、Host 和业务 headers 符合固定契约；
- 请求体为完整 64 KiB，且 hash 正确；
- 响应体为完整 64 KiB，客户端重新计算的整体 SHA-256 与 `X-Bench-Response-Body-SHA256` 一致；
- HTTP 使用绝对式请求；HTTPS 使用 CONNECT 后的 TLS/HTTP/2 origin-form 请求；
- `X-Bench-Sticky-ID` 来自测试上游对实际 `Proxy-Authorization` 粘滞会话 URL 的解析，不是测试程序临时生成的值；
- 返回的 sticky ID 等于 MITMRouter 根据测试 Marker 推导的 ID；
- 本报告全部样本 errors 为 0。

## 5. 怎么复现

先跑小规模正确性检查：

```bash
MITMROUTER_RUN_BENCHMARK=1 GOCACHE="$PWD/.gocache" \
  go test ./internal/server \
  -run '^TestIndependentBenchmarkThroughMITMRouter$' -count=1 -v
```

再跑正式多组实测：

```bash
MITMROUTER_RUN_BENCHMARK=1 GOCACHE="$PWD/.gocache" \
  go test ./internal/server -run '^$' \
  -bench '^BenchmarkIndependentBenchmark$' \
  -benchtime 2s -count=3 -v
```

测试会自动编译并启动根目录的 `benchmark`，不需要手工启动它。完整的测试设计、数据契约和指标说明见 [008-benchmark-system.md](008-benchmark-system.md)。

## 6. 别把这份报告当成什么

这份数据不是线上容量承诺，原因很简单：测试上游在本机，不访问公网，也不跑真实模型。生产环境还会受到这些因素影响：

- 真实住宅出口的并发上限、带宽、会话失效和限流；
- 公网 RTT、丢包、跨地区路由和 TLS 重传；
- 模型首 token 和流式输出速度；
- 服务器 CPU、内存、FD 上限、磁盘和 SQLite 审计负载；
- 同机其他任务造成的调度竞争。

上线前应该在目标机器上重新跑同一条命令，并把结果和本机结果分开保存。对业务来说，优先看自己的首字节 SLO；如果并发 256 虽然 IOPS 更高、但首字节已经不能接受，就应该选 64 或更低的并发档位。
